Starting point

The first part of the project was done in an earlier chat. It left a solid base:

  • The full schema in studiamo.sql: enums, triggers, the player_levels and student_courses views, and the exp rules written as a comment.
  • An ORM model and DTOs for every table, the Db helper, and automatic Alembic migrations on startup.
  • One finished service, CourseService, with 19 passing checks. That was the reference for everything else.

Two things in it did not work yet. UserDto used EmailStr without the email-validator package, so importing it crashed. UserRole.ADMIN existed in Python but not in the Postgres enum.

Decisions and why

Most of these follow from the schema or from the existing code. The ones marked confirm are choices the schema left open; they are also listed in the next section.

Structure

D1

Copy the CourseService pattern exactly. One service class per area, DTOs in and out, a session per method, a separate errors file.

Why: it was already tested and documented. A second style would make the codebase harder to read, and routes can treat every service the same way.

D2

Every error inherits one of four shared types: NotFound, Conflict, InvalidOperation, PermissionDenied. CourseErrors was updated to match, without changing how it behaves.

Why: the routes can map all errors to 404, 409, 422 and 403 in one handler instead of catching dozens of classes.

D3

Services do not check roles, as in CourseService. The caller passes the logged-in user's id, and the routes decide who may call what (UserService.has_role helps). The exception is ownership: a student can only submit or read their own attempts.

Why: permission rules depend on the route and the session, which do not exist yet. Ownership is checked inside the service because it is part of the data itself.

D4

Steps that belong together run in one transaction. Grading an attempt, updating the mark, writing the exp ledger, raising total_exp and recalculating rank happen together or not at all.

Why: a crash halfway through would otherwise give exp without a mark, or a mark without exp.

D5

Rows that point at each other are locked during sensitive steps. Starting an attempt locks the exercise or exam row; grading locks the attempt and the mark.

Why: two clicks on "Start" or "Submit" at the same moment must not create two attempts, or give exp twice.

Accounts

D6

Passwords are hashed with werkzeug's scrypt, and password_hash never leaves the service.

Why: werkzeug already comes with Flask, so no new security dependency, and scrypt is a sound default.

D7

Emails are stored in lower case, and a failed login gives the same message, and takes the same time, whether the email or the password was wrong.

Why: "Shin@x.com" and "shin@x.com" must be one account, and a login form must not reveal which emails are registered.

D8

Google/GitHub sign-in links to an existing account by email only when the provider says the email is verified. Otherwise it raises EmailTakenError.

Why: without this check, anyone could take over an account by registering its email with a provider.

D9

A user's last way to sign in cannot be removed, and users who authored courses, questions or exams cannot be deleted.

Why: the first would lock the user out for good. For the second, the database has no cascade on those authors, so their content would be left without one.

D10

Migration 0002 adds admin to the user_role enum, and it was applied to the Supabase database.

Why: the DTO comments already describe admin-only role changes, so the role was intended. The change only adds a value, and the app would have run it on its next start anyway.

Content

D11

A question is checked again after every edit. An mcq keeps at least 2 options and 1 correct one (only one unless allow_multiple), and a code question keeps at least 1 test case.

Why: the DTOs check this on create, but options and test cases are edited separately, which could leave a question unanswerable.

D12

Questions in use cannot be deleted; deactivate them instead.

Why: exercises, exam pools and past attempts point at them. Deactivated questions drop out of new exams, and history stays intact.

D13

Topic reordering moves positions in two passes (first to temporary negative values, then to the final ones).

Why: positions are unique within a course, so swapping two topics directly would break that rule halfway through.

D14

An exercise can only be linked to a note of the same course, and a system exam can only use topics of its own course.

Why: the schema allows any pair, but a link across courses would show students content from a course they are not studying.

D15

Publishing an exam checks the pool first: there must be active questions, and enough of them for questions_per_attempt.

Why: otherwise the first student to click "Start" would hit the error instead of the lecturer.

Attempts and grading

D16

Starting again while an attempt is open returns that attempt instead of creating a new one. Options in an exam keep the same shuffled order when it is resumed.

Why: a page reload must not cost a scheduled exam's only attempt, or change the order of the answers mid-exam.

D17

MCQs are graded all or nothing. The selected options must be exactly the correct ones.

Why: the schema has no partial-credit setting, and this is the usual rule. It is one line in Grading.py if you want partial credit.

D18

Short answers are graded by a lecturer confirm. The attempt stays submitted; when the lecturer gives points it becomes graded, and exp is awarded then. Blank answers count as 0 straight away.

Why: the schema stores no expected answer for short questions, and the submitted → graded status already exists for this step.

D19

Code answers run through a pluggable CodeRunner confirm. Points are split by test case weight. Without a runner, code waits for a lecturer like short answers.

Why: running student code inside the web server is unsafe. A sandbox (Judge0, Piston, Docker) is a separate decision, so the code only defines the plug. The tests use a fake runner.

D20

The attempt record is a markdown file with a snapshot of each question, the student's answer, the correct answer or test results, and the points. Only its path goes into md_path. The files are saved on local disk (MARKDOWN_DIR, default data/md) through a small interface that can be swapped for Supabase Storage.

Why: this is what the schema comment asks for. Questions can be edited later, but the record must show what the student actually saw.

D21

The list of questions waiting for a lecturer is kept in a hidden line inside the record (<!-- studiamo:pending 3,5 -->).

Why: individual answers are not stored as rows by design. Guessing from question types would break if a code runner is added between submitting and grading.

D22

Exam deadline: start time plus duration_minutes, and never later than closes_at for scheduled exams. A submission more than 2 minutes late is accepted but its answers are ignored (score 0) confirm. An abandoned attempt past its deadline is closed the same way the next time the student starts the exam.

Why: rejecting a late submission would leave the attempt stuck, and for a scheduled exam it is the only one. The 2 minutes covers network delay and the page's auto-submit.

D23

Exam questions are drawn randomly with a secure random generator, and the drawn set is saved in exam_attempt_questions. A lecturer's points override in the pool applies to that question in the exam.

Why: each attempt must keep exactly the questions it got, even if the pool changes later.

Exp and rank

D24

Exp follows the rules in the schema comment exactly:

note max_exp, once, when completed exercise floor(max_exp × score% × retake_decay^(attempt − 1)) every graded attempt exam floor(max_exp × best score%) − exp already earned only if positive

Why: these were already decided, so the service only implements them. Every award is written to exp_ledger and added to total_exp, so the ledger always adds up to the total.

D25

Rank comes from the average best score across every exercise and exam the student has a mark for confirm. S ≥ 95, A ≥ 85, B ≥ 75, C ≥ 65, D ≥ 50, E ≥ 35, otherwise F.

Why: the schema says "performance_score 0-100 drives rank" but gives no formula. An average is easy to explain to students and to change; all of it is in ExpRules.py.

D26

Ties share a leaderboard position, and the position is computed over all players before the page is cut.

Why: two students with the same exp should both be 3rd, and page 2 must not restart at 1.
